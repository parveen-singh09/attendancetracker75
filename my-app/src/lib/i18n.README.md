# i18n (Phase 1)

A lightweight, client-side i18n system. **Phase 1 only** — see the bottom
of this file for what it covers, what's stubbed, and what comes next.

## Architecture

```
src/lib/
├── i18n.ts            Translation dictionary + helpers (the source of truth)
└── i18n-runtime.ts    Tiny client runtime that swaps text on locale change

src/components/
└── LocaleSwitcher.astro   The dropdown UI + click handlers
```

Pages render in English (the canonical baseline). Each translatable element
carries a `data-i18n="<key>"` attribute. When the user picks a language,
the runtime walks all `[data-i18n]` elements and swaps `textContent` to
the matching translation. The choice is persisted to
`localStorage.at75_locale`.

## Adding a new translation key

1. Add the English entry to `translations.en` in `src/lib/i18n.ts`:

   ```ts
   'btn.saveChanges': 'Save changes',
   ```

2. Mark the element in the page/component with `data-i18n`:

   ```astro
   <button data-i18n="btn.saveChanges">Save changes</button>
   ```

3. (Optional) Translate into other locales. Missing entries fall back to
   English at runtime — no broken UI.

For attribute translations (placeholder, aria-label, etc.):

```astro
<input
  data-i18n-attr="placeholder:auth.signup.namePlaceholder"
  placeholder="e.g. John Doe"
/>
```

Multiple attrs can be declared space-separated:
`"placeholder:k1 aria-label:k2"`.

## Adding a new language

1. Add the new code to `LOCALES` in `src/lib/i18n.ts`:

   ```ts
   export const LOCALES = [..., 'ko'] as const;
   ```

2. Add an empty dictionary in the same file and fill it in:

   ```ts
   const ko: Dict = {
     'nav.today': '오늘의 일정',
     // ...
   };
   export const translations: Record<Locale, Dict> = { en, hi, es, fr, de, pt, ar, zh, ja, ru, ko };
   ```

3. If the language is RTL, add the code to `RTL_LOCALES`:

   ```ts
   export const RTL_LOCALES: ReadonlySet<Locale> = new Set(['ar', 'he']);
   ```

4. Add the option to `LocaleSwitcher.astro`:

   ```ts
   const localeData: Record<Locale, { label: string; flag: string }> = {
     // ...
     ko: { label: '한국어', flag: '🇰🇷' },
   };
   ```

5. `applyToRoot` in `i18n-runtime.ts` already handles the new locale's
   `lang` and `dir` attributes from the new entries.

## How persistence + restoration works

- `localStorage.at75_locale` stores the chosen locale code.
- The pre-paint inline script in `BaseLayout.astro` reads it and sets
  `<html lang>` and `<html dir>` before first paint to avoid the wrong
  font/dir flashing in.
- The LocaleSwitcher's `astro:page-load` handler then re-paints its own
  label/check marks and calls `applyLocale()` to swap the page text.
- After a View Transitions navigation, the `astro:after-swap` event
  re-applies the theme + locale from localStorage.

## Phase 1 scope (what's translated)

Translated in phase 1:
- App nav (Today, Weekly, Subjects, Calculator, Sessions, Settings, Log out)
- Marketing landing (hero, CTAs, bottom CTA card, URL label, badge)
- Auth pages (titles, subtitles, form labels, placeholders, error
  messages, submit button labels, "loading" labels)
- Onboarding welcome + session (titles, body, step labels, form labels)
- Today page (title, "Mark Attendance", "Today's schedule", "Overall
  Attendance", empty-state copy)

## Phase 2 scope (added in 2026-06)

Translated in phase 2:
- Marketing landing long-form copy (the SEO paragraphs on
  `pages/index.astro`). Headlines + 5 long paragraphs + 4 feature
  items. Uses the `data-i18n-emph` attribute + `{emphN}...{emphEnd}`
  markers in the dictionary so the bold/italic markup survives the
  locale swap.
- About page (`pages/about.astro`): full text, all 4 principles.
- Contact page (`pages/contact.astro`): all 4 cards + the heads-up banner.
- Privacy Policy (`pages/legal/privacy.astro`): all 5 section headings
  + the 3 bullet items. Body paragraphs left to fall back to English
  for non-Spanish/French/Hindi locales.
- Terms of Service (`pages/legal/terms.astro`): all 4 section headings
  + short body strings. Body paragraphs left to fall back to English
  for non-Spanish/French/Hindi locales.
- FAQ section (`components/marketing/FaqSection.astro`): the visible
  HTML and the JSON-LD. The Q/A pairs are now driven by i18n keys;
  the JSON-LD is server-rendered in English (canonical SEO copy) and
  the visible HTML uses `data-i18n` so the user sees the translated
  copy.

## Phase 2 scope (what's intentionally not translated)

- Long FAQ answers in Arabic, Chinese, Japanese, Russian — only the
  questions and a few headlines are translated; the answers fall back
  to English. Recommend a native speaker review.
- Marketing long-form body paragraphs in German, Portuguese, Arabic,
  Chinese, Japanese, Russian — only headlines are translated. Body
  falls back to English.
- React island components (WeeklyGrid, SubjectQuickMarks, etc.). The
  WeeklyGrid "Save & Continue" button is still a static English string.
- Server-rendered error responses (e.g. "An account with that email
  already exists."). These come from the API and are shown as-is.
- Date/number formatting. (We use `Intl.DateTimeFormat` already; locale
  changes affect which calendar/locale the browser uses for those.)

## New attribute: `data-i18n-emph`

For paragraphs with inline emphasis, use:

```astro
<p data-i18n-emph="about.principle1">
  <strong>Free, forever.</strong> No paywall, no Pro tier, no ads.
</p>
```

The dictionary entry uses `{strong1}...{strongEnd}` for `<strong>` or
`{emph1}...{emphEnd}` for `<em>`. The runtime parses the
translated string and re-builds the children, preserving markup:

```ts
'about.principle1': '{strong1}Free, forever.{strongEnd} No paywall, no Pro tier, no ads.',
```

`{strongN}` and `{emphN}` markers can be combined in any order; the
runtime stitches them back into the DOM. Multiple markers are
supported via incrementing N (`{emph1}...{emphEnd}`, `{emph2}...{emphEnd}`).

## Why not per-locale URL routes?

Per-locale URL routes (`/en/about`, `/es/about`) are the most "correct"
architectural answer — but they require duplicating every page route
and a routing helper. For phase 1, a client-side dictionary is the
cheapest way to give the user a working language switcher with
meaningful coverage. The DESIGN.md already says "structure i18n keys
from day one so v2 is cheap" — and now we have a key scheme that's
v2-compatible: we can flip to per-route translations later without
having to re-key everything.

## Limitations / known issues

- **Flash of English on first paint.** The runtime is a module, so it
  loads *after* the initial paint. A tiny English→target-locale flash
  is possible. Inlining the full dictionary would eliminate it but
  would balloon the script size.
- **Locale is per-browser, not per-user.** Server-rendered pages always
  come back in English. A future phase could read the `Accept-Language`
  header and SSR in the user's locale.
- **No translation quality tooling.** Translators need to add entries
  by hand. Consider adding a CI check that fails when a new key is
  added to `en` but missing in too many other locales.

## Testing

- `astro check` validates that the modules compile (no missing imports
  / type errors).
- Manual: open the app, click the globe icon in the header, pick a
  language. The visible text in the nav + page chrome should change
  immediately, the choice should persist on reload, and the `<html
  lang>` attribute should reflect the choice.
